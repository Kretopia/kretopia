# Kreto New Room State Mapping Audit

## Status: `AUDITED`. Several states map cleanly to `VoiceFirstCreateModal.tsx`'s existing real state; two require a product decision before they can be implemented honestly; one (`listening`) does not exist in `KretoPresence` yet.

Read in full for this pass: `src/components/project/studio/VoiceFirstCreateModal.tsx` (1200 lines). Its own `mode` state machine is `"prompt" | "recording" | "thinking" | "review"`, backed by real `getUserMedia`, real `supabase.functions.invoke("extract-brief", ...)` calls, and real `analytics.newRoom*` events at every transition (`newRoomVoiceStarted`, `newRoomDraftReady`, `newRoomProjectConfirmed`, `newRoomCreationFailed`, etc.) — meaning the trigger points the brief wants Kreto's states tied to already exist as concrete, instrumented code paths, not something that needs new plumbing to observe.

## Mapping table

| Brief state | Real trigger in `VoiceFirstCreateModal.tsx` | Status |
|---|---|---|
| `idle` | `mode === "prompt"`, before any input | Clean mapping. |
| `attentive` | User focuses the text composer or taps an inspiration chip / mode selector, before submitting | Clean mapping — `mode === "prompt"` with the input focused is real, observable DOM state (the input already has `autoFocus`; a focus/blur handler would make "user is actively composing" real and checkable). |
| `listening` | `mode === "recording"` — this only becomes true after `getUserMedia({audio:true})` **resolves successfully** (the `try`/`catch` in `startRecording()` never sets `mode="recording"` on a permission denial or missing mic — it shows a toast and stays in `prompt`) | **Clean mapping, but `listening` does not exist in `KretoPresence`'s current 8-state enum** (`idle/attentive/processing/proposal_ready/success/caution/error/offline`). This is the one genuinely new state this surface needs — see "What needs building" below. |
| `processing` | `mode === "thinking"` — covers all four real async paths: `processAudio`, `submitText`, `processFile`, `submitLink`, each a real `supabase.functions.invoke` call | Clean mapping. Note: `VoiceFirstCreateModal.tsx` already renders its own Kreto presence here today — `<KretoMark size="xl" state="active" />` — using the older flat mark, not the embodied `KretoPresence`. See `KRETO_NEW_ROOM_INTEGRATION_REPORT.md`. |
| `proposal_ready` | `mode === "review"` with a non-empty `brief.project.title` | Clean mapping — this is the real "a draft was returned" moment in all four intake paths. |
| `caution` | Ambiguous — **requires a product decision**. Two real candidates exist: (a) `brief.deliverables` came back empty (the code already renders a distinct "We couldn't pull starter tasks from that..." panel for this case — line ~1028), or (b) the Create buttons are disabled because `paymentsInvolved === null` (a real, currently-unanswered required field gating submission). Both are real "needs your review before this can proceed" moments, but they're different moments (draft quality vs. a required field), and the brief's "caution" is meant to be a single state — using it for both would conflate two different reasons with one signal. | Needs a decision: pick one, or don't use `caution` on this surface and let the existing inline copy (already present, already real) carry that meaning instead. |
| `success` | `createProject()`'s success path — **but the modal closes immediately** (`onOpenChange(false)`) and navigates away 80ms later (`setTimeout(() => navigate(...), 80)`). There is no time window where the modal is open and could show a "success" Kreto state. | **Requires a product decision**: either (a) delay the close by long enough to show a brief success acknowledgement (changes existing, deliberate UX — the 80ms delay is already tuned for a specific "close then land" feel), or (b) show `success` on the *destination* page (`/desk/:projectId`) instead of in this modal, which is a different component and a different, separately-scoped integration. Not decidable unilaterally. |
| `error` | `processAudio`/`submitText`/`processFile`/`submitLink`/`createProject`'s `catch` blocks — all real failures, all already correctly instrumented (`analytics.newRoomCreationFailed(...)`) | The failures are real, but **there is no distinct visual "error" mode today** — every catch block shows a `toast` and reverts `mode` to `"prompt"` (or stays in `"review"` for a creation failure). Mapping `error` here means either introducing a short-lived error flag alongside the toast (a small, real addition — not fabricated, since it would only ever be set inside an existing real catch block) or intentionally leaving `error` to the toast alone on this surface and not adding a visual Kreto error state here. Implementation choice, not blocked, but not decided. |
| `offline` | No real signal exists. Confirmed (again) via `grep -rn "navigator.onLine" src/` — no connectivity tracking anywhere in this codebase. | Same finding as `KRETO_STATE_MACHINE_REPORT.md`'s prior pass: implementable once a real signal exists, not before. A failed `supabase.functions.invoke` due to being offline currently surfaces through the same generic `error` catch path as any other failure — there is no way to distinguish "offline" from "the edge function returned an error" without new detection logic, which would be new behavior, not a read of existing state. |

## What needs building (not done in this pass — audit only)

1. **A `listening` state added to `KretoPresenceState`** (and its `SIZE`/`signalColor`/`signalMotion`/`STATE_LABEL` entries) — the only clean, unambiguous, zero-decision-needed net-new state this surface requires. Visually distinct from `processing` (the brief separates "capturing your voice" from "thinking about what you said" — a real, meaningful distinction users can feel the difference between).
2. Everything else above either has a clean mapping already (`idle`, `attentive`, `processing`, `proposal_ready`) or needs an explicit product decision before implementation (`caution`, `success`, `error`, `offline`) — see `KRETO_NEW_ROOM_INTEGRATION_REPORT.md`'s recommendation.
